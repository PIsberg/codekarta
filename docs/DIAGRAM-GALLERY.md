# Diagram Gallery

Every diagram below is generated by code-karta **from code-karta's own source**, so each one
doubles as a worked example and as a regression check on the tool.

> The SVGs in `docs/diagrams/` are regenerated by the build; this page is written by hand and
> only points at them.
>
> **Regenerate the diagrams:** `mvn verify -DskipTests` or `./gradlew :code-karta-cli:generateDiagrams`
>
> **Skip generation:** `mvn verify -DskipTests -DskipDiagrams=true` or `./gradlew :code-karta-cli:generateDiagrams -PskipDiagrams`

The pipeline that produces them:

```text
code-karta-core    -> pure IR data model: Graph, Node, Edge, Group
code-karta-input   -> Java source parsing into the IR
code-karta-layout  -> coordinate assignment
code-karta-render  -> SVG output
code-karta-cli     -> command-line orchestration
```

No tier imports from a sibling or from a tier above it. The `Graph` object is the only contract
that crosses tier boundaries — see [`ARCHITECTURE.md`](ARCHITECTURE.md) for the full rationale.

## 4. Parser Call Chain — Call-Only Sequence Diagram

Generated from `CallSequenceParser.java` with `--sequence-only`:

```bash
java -jar karta.jar \
  --input code-karta-input/src/main/java/se/deversity/codekarta/input/parser/CallSequenceParser.java \

```

`--sequence-only` emits ordered `CALLS` edges without exception-flow analysis. Use it when a compact
call graph is more useful than exception propagation details.

## 5. Cross-File Call Graph — Multi-File Stitched Sequence

Generated from the shipping example `core` package with `--sequence-only`:

```bash
java -jar karta.jar \
  --input example-shipping-system/src/main/java/com/karta/shipping/core \
  --output docs/diagrams \
  --sequence-only
```

Directory input plus `--sequence-only` parses all Java files below the directory into one graph.
JavaParser's symbol solver is anchored at the input root so resolved callees use qualified
`ClassName.method` node IDs — calls from `OrderProcessor` to `InventoryService` connect across file
boundaries rather than dangling as unowned nodes.

For accurate cross-package resolution, point `--input` at a source root such as `src/main/java`
rather than a nested package.

![OrderProcessor→InventoryService cross-file stitched sequence](diagrams/sequence-diagram.svg)

## 6. State Machine Diagrams

Generated from `KartaCli.java` using `--state-machine`:

```bash
java -jar karta.jar \
  --input code-karta-cli/src/main/java/se/deversity/codekarta/cli/KartaCli.java \
  --state-machine --output docs/diagrams
```

`KartaCli` tracks its own execution as a `PipelineStage` enum with five constants. Sequential
assignments in `run()` drive `StateMachineParser`'s linear-assignment detection:
`PARSING → LAYOUT → RENDERING → WRITING → DONE`.

![KartaCli pipeline state machine](diagrams/kartacli-state-machine-diagram.svg)

`StateMachineParser` recognises three distinct patterns, one per fixture in the shipping example —
switch-case transitions, an explicit `transition(from, to, event)` DSL, and linear state
assignments. See [`EXAMPLE-PROJECT.md`](EXAMPLE-PROJECT.md) for the three worked cases.

## Layout Engines

Two layout engines implement `LayoutEngine` and are selected with `--layout`.

| Flag | Engine | Algorithm |
|---|---|---|
| `--layout simple` | `SimpleLayoutEngine` | Breadth-first depth levels arranged in a row/column grid. This is the default. |
| `--layout elk` | `ElkLayoutEngine` | Eclipse Layout Kernel layered layout with crossing reduction and routed edges. Falls back to simple layout on failure. |

ELK is recommended for large or dense graphs where the simple grid becomes too wide.
