# Contributing to code-karta

Thanks for considering a contribution. This page covers what the build expects, so a pull request
does not fail on something that could have been caught in five minutes locally.

## Before you start

- Open an issue first for anything larger than a bug fix. The three-tier architecture constrains
  where a change can live, and it is cheaper to agree on the tier before the code exists.
- Small fixes, typo corrections and documentation improvements need no issue.

## Local setup

JDK 21 is required to build. The four library modules compile for Java 17 so they can be
consumed from a Java 17 application; only `code-karta-cli` needs 21 at runtime. See
[`COMPATIBILITY.md`](COMPATIBILITY.md) for what that guarantees and the one ELK caveat.

```bash
git clone https://github.com/PIsberg/codekarta.git
cd codekarta
./mvnw clean verify
```

`./mvnw clean verify` is the same gate CI runs. If it passes locally on JDK 21, it should pass in CI.

Use the wrapper rather than a system Maven. The SpotBugs plugin declares a Maven 3.8.9
prerequisite and fails with a bare `PluginIncompatibleException` on anything older; the wrapper
pins 3.9.11. Build on JDK 21 through 25, not 26 or newer: JaCoCo cannot instrument class files
from a much newer JDK and reports it as an error that reads like a defect here. `./mvnw validate`
checks both and says which one is wrong.

See [`docs/BUILD.md`](docs/BUILD.md) for Gradle and for running from source.

## What the gate checks

| Check | Fails when |
|---|---|
| Checkstyle, PMD, SpotBugs, Error Prone | Style or static-analysis findings |
| JaCoCo | A module drops below its `jacoco.line.minimum` |
| ArchUnit (`ArchitectureRulesTest`) | A tier imports from a sibling or from a tier above it |
| Idempotent regeneration | Regenerated diagrams or guardrail files differ from what is committed |
| Build parity | `pom.xml` and `build.gradle.kts` name different versions |
| PIT (separate CI job) | A module drops below its `pitest.mutation.minimum` |

Coverage and mutation numbers in the poms are floors, not targets. Raise one when the measured
number rises. Never lower one to turn a red build green.

[`docs/QUALITY.md`](docs/QUALITY.md) explains each gate and the reasoning behind it.

## Architecture rules

The pipeline is strictly tiered, and `ArchitectureRulesTest` enforces it with ArchUnit rather than
convention:

```
code-karta-core       <- pure data model, no logic, no dependencies
      ^         ^          ^
code-karta-input  code-karta-layout  code-karta-render
                                           ^
                                     code-karta-cli
```

No tier may import from a tier beside or above it. `Graph` is the only object that crosses a tier
boundary. [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) has the full rule set and a table of which
module a given change belongs in.

## Tests

- Every behaviour change ships with a test. A bug fix without a regression test is not finished.
- Write the failing test first where practical, and confirm it goes red before the fix goes in.
- Assert what a caller can observe, not how the code is structured internally. `code-karta-render`
  is the cautionary example: 95.8% line coverage and a 24.1% mutation score, because its tests
  called the renderer and asserted almost nothing about the SVG that came back.
- New tests go in the existing suite so they run in CI.

Run one class with `./mvnw -pl <module> -Dtest=<Class> test`.

## Generated files

Everything between `VIBETAGS-START` and `VIBETAGS-END` markers in `CLAUDE.md`, `GEMINI.md` and
`llms.txt` is generated by the VibeTags annotation processor on every compile. Do not hand-edit
inside the markers. Change the annotation in the Java source and recompile. The same applies to
`docs/diagrams/`, which `mvn verify` regenerates. CI fails if regenerated output differs from what
is committed, so run `mvn clean verify` and commit the result.

## Commits and pull requests

- Branch from `main`. Do not commit to `main` directly.
- Conventional Commits for the subject line: `fix:`, `feat:`, `docs:`, `chore:`, `refactor:`,
  `test:`, `perf:`, `build:`, `ci:`.
- The body explains why the change exists, which failure it prevents, and how it was verified. The
  diff already shows what changed.
- Add a `CHANGELOG.md` entry under `## [Unreleased]` for anything a consumer would notice.
- If the pull request leaves work behind, open an issue for it and link it. Prose in a merged pull
  request body is not a backlog.

## Public API changes

`code-karta-core` is the published contract. Changing a public signature there, or a `NodeType` /
`EdgeType` string value, or a CSS class name emitted by `SvgRenderer`, breaks downstream consumers.
[`COMPATIBILITY.md`](COMPATIBILITY.md) states what is covered by semantic versioning and what is
not. Such a change needs an issue and a deprecation path, not just a passing build.

## Reporting security issues

Do not open a public issue. See [`SECURITY.md`](SECURITY.md).
